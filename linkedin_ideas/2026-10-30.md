What if CALCULATE could read your mind?

I spent a week chasing a metric that kept changing its value after a single slicer selection. The culprit? Implicit filter context sneaking in where I didn’t expect it. Try replacing a plain SUMX with CALCULATE(SUMX(...), ALLSELECTED(Date)) and watch the numbers line up.

## Idea 2 — Power BI & DAX
**Topic:** When to Choose Columns Over Measures

**Hook:** Columns or measures – the choice that breaks your model.

**Full Draft:**

Columns or measures – the choice that breaks your model.

Early in my career I added a calculated column to flag “high‑value” customers. The report ran fine in a sandbox, but once the data grew to millions of rows, refresh times doubled.

Lesson learned: calculated columns are stored on disk and recomputed only on load, while measures calculate on the fly. If the logic depends on slicer interaction, a measure is usually cheaper. Use columns for static flags that never change per row; use measures for anything that needs to react to user filters.

Next time you’re tempted to drop a new column, ask yourself: will this value ever need to change with a visual filter? If yes, go measure.

How do you decide between the two in your models? Drop a comment.

Your report loads slower than coffee on a Monday.

I once inherited a dashboard that took 45 seconds to open. The culprit? Too many visuals pulling from the same large fact table, plus a handful of heavy DAX expressions.

First, I switched to aggregated tables for the high‑level visuals and set visual‑level filters to limit row‑counts. Second, I replaced nested IF statements with SWITCH, which reduced calculation steps. Finally, I turned on “Auto Date/Time” off and built a dedicated date dimension.

After these tweaks the same dashboard now renders in under 8 seconds – a 5× speed boost.

## Idea 5 — Microsoft Fabric & Analytics Engineering
**Topic:** Building a Medallion Pipeline in Fabric

**Hook:** Turn raw data into trusted assets with three simple layers.

**Full Draft:**

Turn raw data into trusted assets with three simple layers.

I recently built a medallion architecture on Fabric: Bronze for raw ingestion, Silver for curated transformations, and Gold for analytics‑ready tables. Using Fabric pipelines, the Bronze stage copies files into OneLake, the Silver stage runs dbt‑style SQL scripts to standardize schema, and the Gold stage materializes aggregates that Power BI consumes.

Key takeaways: • Keep transformation logic versioned in a Git repo – Fabric pipelines pull directly from it. • Use incremental loads on Silver tables to avoid re‑processing the whole dataset. • Expose the Gold layer through a semantic model so downstream users never see messy tables.

The result? A single source of truth that scales with our data volume and cuts report latency in half.
