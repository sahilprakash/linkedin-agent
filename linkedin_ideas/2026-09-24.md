**Hook:** A 2‑second report refresh can become a 0.2‑second sprint.

**Full Draft:**

A 2‑second report refresh can become a 0.2‑second sprint.

The secret?  Trim unnecessary row context and push calculations to the storage layer.  Here are two quick wins:

🔹 **Use VAR to cache intermediate results** – instead of repeating the same expression in multiple measures, store it once.  This cuts evaluation time dramatically.

🔹 **Replace FILTER with CALCULATETABLE when possible** – CALCULATETABLE respects existing relationships and often runs faster because it avoids the full table scan.

I applied these tricks to a sales dashboard with 1.2 M rows.  Refresh time dropped from 2.3 seconds to 0.18 seconds, and the user experience felt instant.

## Idea 5 — Power BI & DAX
**Topic:** Calculated Column vs Measure: When to Choose Each

**Hook:** Stop mixing columns and measures – they’re not interchangeable.

**Full Draft:**

Stop mixing columns and measures – they’re not interchangeable.

A calculated column lives row‑by‑row at load time; a measure calculates on the fly, respecting the current filter context.  Use a column when you need a static attribute (e.g., fiscal quarter derived from a date) that other calculations will reference.

Use a measure when the result must adapt to slicers, drill‑throughs, or visual level filters – like a rolling 12‑month revenue or a dynamic % of total.

Example: `Profit Margin = DIVIDE([Profit],[Revenue])` is a measure because the denominator changes with every visual filter.  Converting it to a column would lock the margin to the base data, producing misleading numbers.

Understanding this split saved me hours of debugging and kept my models lean.

Do you have a scenario where you chose the wrong type and paid the price?
