**Full Draft:**

CALCULATE is not magic; it's a context switch. Here's the mental model.

Most DAX users memorize CALCULATE filters without understanding what happens inside.

When you write:
Sales Amount = SUM(Sales[Amount])
and then use:
CALCULATE([Sales Amount], Customer[Segment] = "Premium")

CALCULATE transforms the current row context into filter context. That's context transition. It's why measures behave differently from calculated columns.

Calculated columns are evaluated row by row, with no awareness of slicers or filters. Measures are evaluated in filter context — so they respond to the report.

If you're new to DAX, stop using calculated columns for logic that needs user interaction. Move that logic into measures.

The next time a measure returns a blank unexpectedly, ask: what filter context is active? Trace it with CALCULATE.

Once you see it, CALCULATE becomes easier to debug.

## Idea 2 — Power BI & DAX
**Topic:** Measures vs calculated columns performance guide

**Hook:** Calculated columns are eating your report's performance. Here's the fix.

**Full Draft:**

Calculated columns are eating your report's performance. Here's the fix.

Every calculated column you add to a large table gets evaluated during refresh and stored in memory. It doesn't dynamically respond to slicers. It doesn't reuse filter context. It just sits there, taking space.

Measures, on the other hand, are calculated at query time. They respect filters, scale with user interaction, and use the VertiPaq engine efficiently.

Why does this matter? Because every extra calculated column increases your model size and slows down cross-filtering. The effect compounds as your data grows.

Rule of thumb:
- Use calculated columns for row-level constants like categorization by static thresholds.
- Use measures for anything that sums, averages, counts, or changes with a filter.

I've seen reports go from 12 seconds to under 2 after moving a few heavy calculated columns into measures.

If you're rebuilding a slow Power BI report, start there.

## Idea 3 — Power BI & DAX
**Topic:** Write cleaner DAX with variables now

**Hook:** Your DAX will read better if you use VAR. Try this pattern.

**Full Draft:**

Your DAX will read better if you use VAR. Try this pattern.

Too many measures are long chains of CALCULATE and FILTER with no clear steps. You end up repeating logic and wondering where the bug is.

VAR lets you name intermediate results. The measure evaluates those results once, then reuse them.

Example:
Revenue =
VAR UnitPrice = SUM(Products[Price])
VAR Quantity = SUM(Sales[Quantity])
RETURN
UnitPrice * Quantity

This isn't just about readability. It can also improve performance because DAX doesn't recalculate the same expression multiple times.

VAR also makes context transition easier to trace. You can assign a piece of logic to a variable, test it in isolation, and then combine it with CALCULATE.

When you come back to that measure in three months, you'll thank yourself.

A quick debugging trick: temporarily change RETURN to one of your variables. You'll see exactly what that step produces.

If you're just starting with DAX, make VAR/RETURN your default. It forces you to break down the problem instead of nesting everything into one expression.

## Idea 4 — Microsoft Fabric & Analytics Engineering
**Topic:** Medallion architecture in Microsoft Fabric explained

**Hook:** Bronze, Silver, Gold is not a hierarchy of value.

**Full Draft:**

Bronze, Silver, Gold is not a hierarchy of value.

In Microsoft Fabric, the medallion architecture often gets misunderstood. People think Gold is more important than Bronze. It's not—it's about layers of transformation.

Bronze: raw data as it lands, no cleaning.
Silver: cleansed, deduplicated, conformed data.
Gold: business-ready models, aggregates, semantic models.

The key is to keep your layers separate in OneLake. Use shortcuts to reference data without copying it everywhere. That saves storage and keeps a single source of truth.

Gold isn't the final stop. It feeds semantic models, Power BI reports, and machine learning. So the quality of your Gold layer decides how much work downstream becomes.

When I design Fabric solutions, I think like an analytics engineer: each layer has one responsibility, and data moves through it with clear contracts.

If you're building a Lakehouse, start with medallion. It gives you a backbone for everything else.

## Idea 5 — Microsoft Fabric & Analytics Engineering
**Topic:** Fabric semantic models need analytics engineering

**Hook:** Your Fabric semantic model is only as good as your data preparation.

**Full Draft:**

Your Fabric semantic model is only as good as your data preparation.

I've seen Power BI reports sit on top of messy Fabric Lakehouses. The semantic model becomes a dumping ground—dozens of tables, unclear relationships, bad DAX.

Analytics engineering changes that. Instead of loading raw data into a semantic model, you transform it first.

Think dbt-style:
- Keep transformations in Silver/Gold layers with clear naming.
- Test data quality—nulls, duplicates, row counts.
- Document every table and column.
- Version control your code so changes are traceable.

Microsoft Fabric makes this easier with notebooks and data pipelines. But the discipline still comes from the engineer.

If you're building semantic models in Fabric, invest in the transformation layer before you build a single measure. Your measures, relationships, and row-level security will all behave better when the data underneath is trustworthy. Start with the data, not the visuals.
